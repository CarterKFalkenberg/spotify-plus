# Spotify Plus visual design

The redesign for [issue #63](https://github.com/CarterKFalkenberg/spotify-plus/issues/63) replaces the previous cream and sage interface with a compact music workspace. It takes cues from the clarity of Apple software and Spotify's emphasis on the collection, while retaining its own navigation, composition and typography. The [product brief](PRODUCT-BRIEF.md), [accepted decisions](DECISIONS.md), and [everyday flows](UX-FLOWS.md) define behavior. This is a frontend redesign, not a change to Spotify contracts, tagging semantics or playlist guarantees.

## Composition

The desktop application uses a restrained graphite or neutral navigation rail. Account access and appearance sit in the header; sync status stays above the current task. The rail does not become a second dashboard. On phones, five compact bottom destinations keep playlist composition, playlists, new arrivals, library and vocabulary accessible without consuming the top half of the screen. Account access remains a named disclosure; mobile arrival tagging remains a native modal sheet.

Each surface has a different composition serving its task:

- **Queue:** large square artwork and track identity occupy one column. The other is a tagging desk: current tags, immediate-save reassurance, autocomplete, and nine keyboard slots in a compact three-column grid. Previous/Next/Skip form a separate navigation group; Spotify, artist and help tools sit below it. Count-up session feedback remains in the heading. No playback controls or invented listening state appear.
- **Library:** edge-aligned collection rows, with artwork and song identity leading metadata, tags and editing. Grouped artist/album/decade results become compact ledger rows with tagging controls beside identity, rather than independent cards. Search, membership, untagged and grouping remain first-class controls; facets expand in place. Frozen selection, tri-state add/clear, and changed-only undo retain their existing handlers and sticky dock.
- **Builder:** the desktop query composer and song preview sit side by side. All/Any/None are compact ruled sections; they do not look like three feature cards. The count and duration lead the preview. Playlist name, retention and creation follow the query/preview together, with publication and snapshot qualifications visible. On phones these sections flow in query, preview, details order with a sticky match count.
- **Playlists:** a collection ledger aligns name/query, status/count, expiry and creation date. Spotify is the principal action, with retention and regeneration controls subordinate. Pending, incomplete and removal states retain literal text and separate visual treatment; Ready never means independently proven profile/search hiding.
- **Vocabulary:** dictionary rows pair the tag string and usage/last-use metadata with contextual management and explicit merge-source selection. Tags stay flat and uncolored. Rename, merge, previewed impact, deletion confirmation and undo continue to use the existing domain operations.

Connection, account, policy, empty and error views share the same typography, materials and controls. The connection screen explains the actual workflow without a marketing hero, numbered feature ceremony, decorative gradients or fake player imagery. Destructive actions stay in named native confirmation dialogs.

## Appearance and shared controls

Appearance is a device preference, exposed through the named **Appearance** select on every page. Its choices are **System**, **Light**, and **Dark**. The initial choice is System. The choice persists under `spotify-plus-theme` in local storage when available, follows changes from another tab, and responds to OS appearance changes only while System is selected. Invalid or unavailable storage falls back to System; an explicit current-visit choice still works when persistence is unavailable.

A small blocking `appearance.js` bootstrap resolves the preference before application styles and React render. The React control consumes the same resolver, avoiding two independent implementations. It sets the document theme, native `color-scheme`, and browser theme-color together. This application is client-rendered; there is no server hydration state to disagree with the selected appearance. The bootstrap also avoids rendering the wrong appearance while session state loads.

Light uses a cool neutral canvas, white work surfaces and near-black type. Dark uses graphite canvas, slightly raised charcoal surfaces and warm-white type. Supporting text remains readable rather than decorative. Artwork supplies the broad color. Green is reserved for principal actions, active navigation, connection indicators and the quiet new-arrivals marker; tags never acquire color identity.

`--control-line` identifies enabled fields separately from decorative `--line` dividers. All inputs, selects, placeholders and supporting text must meet the existing rendered contrast assertions. Focus uses a visible three-pixel outline independent of hover and selected states. Applied tags, selected autocomplete options, bulk tri-state text, checked boxes and saved/undo feedback communicate state beyond color. Native disabled semantics and busy states remain intact. Reduced-motion preferences suppress motion.

## Evidence and verification

Before/after proof uses synthetic fixtures only. Real Spotify names, library metadata, images and credentials never enter screenshots or model context. Matching baseline and final captures, exact source provenance and explanations are published with the PR and linked in the delivery response. The [detailed captioned proof gallery](design/proof/README.md) includes 22 comparisons and their source/hash manifest under `docs/design/proof/`.

Browser checks continue to measure resolved text contrast, enabled field borders, placeholder contrast, focus, reflow, modal behavior, keyboard/IME safety, selection/undo and navigation hierarchy. Both palettes cover authenticated library, bulk selection, builder suggestions, playlist states, queue applied tags and suggestions, vocabulary and destructive confirmation. Geometry checks cover desktop account/appearance separation, phone task and primary-action clearance, focused sheet suggestions, group Browse targets, and the separate saved-feedback row at 600px and 720px desktop heights.

The sticky bulk editor bounds its scrolling controls while preserving visible Undo feedback. Group feedback occupies a separate left-hand region from the group picker. In-flow picker menus remain stable through a pointer press: closing the menu on blur used to shrink the sticky editor between pointerdown and click, losing the outside button's click. The picker now closes after that gesture finishes, while keyboard blur closes immediately; cancellation, frame and document-listener cleanup are explicit. The frozen-revision reselection regression continues to require the owner's actual click before adopting a refreshed filter result. Appearance checks cover System/OS changes, explicit preferences, reload/navigation persistence, native color-scheme and unavailable/invalid storage. Existing behavior assertions remain acceptance gates; changes to markup require equivalent behavior and accessibility evidence, not weaker tests.

The orchestrator independently owns full checks, visual critique, pinned Standards/Spec review, exact-head CI, deployment and redacted live verification. Actual phone keyboard behavior and the under-one-minute phone flow, familiar-song tagging at roughly 3–5 seconds per song, and actual profile/search hiding remain **pending human product acceptance**. Emulation and acknowledged publication commands cannot establish those outcomes.

## Guided task composition — issue #67

The October 21 overhaul follows the user's [accepted workflow direction](DECISIONS.md#guided-everyday-workflows--october-21-2026). The three builder stages are Choose tags, Review songs, and Name & keep. Each stage exposes one primary action and Back preserves the draft. All of remains the starting point; an explicit refinement control reveals Any of and None of, including a count when populated refinements are collapsed. The live count and duration remain visible throughout. Review uses the same cached preview and exclusions; creation still validates the current preview revision and persists the exact request before transmission. Stage transitions never submit the create form. Narrow or enlarged content can scroll instead of being clipped.

Library browsing has explicit Songs, Artists, Albums, and Decades destinations. Requests are bounded to 12 groups or 30 songs, with Previous/Next page controls. Changing a filter or browse mode resets paging; all-matching selection continues to capture the entire matching filter and its revision, rather than the visible page. Group rows expose Tag songs and Browse songs, opening a single shared selection editor instead of mounting a tag search on every group. Artwork is contained and linked to Spotify; placeholders describe unavailable artwork rather than inventing an artist portrait.

The queue retains large art, immediate tagging, quick slots, and a dominant Next. Queue settings and Song actions disclose secondary controls. Open in Spotify has one explicit visible link. Healthy playlist rows show artwork, identity and expiry, Open in Spotify, and a per-playlist Manage disclosure; retention drafts belong to that playlist. Incomplete, blocked, removing, and ambiguous-request states retain literal explanations and retry actions. Healthy Ready badges are omitted. Tag rows retain one contextual edit entry and usage count.

Appearance now uses an icon-triggered, named disclosure with System, Light and Dark radio options. The preference resolver, pre-paint bootstrap, persistence, cross-tab and OS behavior remain unchanged. Both palettes share the same hierarchy and accessible selected states.

Verification evidence is collected after the candidate is rendered and independently critiqued. Source changes or a passing test run alone are not visual acceptance, actual phone acceptance, or proof of Spotify publication hiding.

# Spotify Plus visual design

Visual refinement for [issue #60](https://github.com/CarterKFalkenberg/spotify-plus/issues/60), building on the [everyday flows](UX-FLOWS.md). The cream canvas, forest ink, lime ready/new accents, system font and existing layout remain the design. This pass makes fields easier to recognize, working text easier to read, and action/status hierarchy consistent. Product behavior and publication qualifications remain those of the [brief](PRODUCT-BRIEF.md) and [accepted decisions](DECISIONS.md).

## Tokens, type and state conventions

`--ink` (`#193c34`) identifies primary actions and meaningful content. `--muted` (`#566653`) supplies readable supporting content; `--paper` (`#fffef8`) and `--wash` (`#eaf0df`) separate cards and selected/secondary regions. `--accent` stays reserved for new/ready emphasis, without introducing tag colours. `--control-line` (`#77866e`) identifies fields; `--line` remains decorative. Enabled field borders measure 3.84:1 against paper and 3.33:1 against wash. Muted text measures 6.08:1 against paper and 5.27:1 against wash. Tests use unrounded rendered values for pass/fail.

The shared 3px focus outline remains distinct from hover and selected states. Hover darkens enabled field boundaries; it does not remove keyboard focus. Native disabled controls and busy read-only tag inputs have a neutral fill and retain explicit disabled semantics. Selected autocomplete rows use wash plus `aria-selected`; bulk tri-state wording, explicit Clear, native checkboxes and saved/undo feedback provide meaning beyond colour. Errors retain textual explanations and recovery controls; destructive confirmations retain named native dialogs and the red confirm action. Reduced-motion settings suppress animation/transition/scroll effects.

The contrast targets follow W3C's [non-text contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) for identifying controls/states and [contrast minimum guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) for text. Decorative dividers and disabled controls are distinct cases. This bounded review is not a complete WCAG conformance audit.

## Evidence and acceptance boundary

Ignored synthetic evidence lives in `.local/ui/before/` and `.local/ui/after/`; each directory has a provenance manifest. The baseline was captured from clean `c96ad51cb675fd8d491748ffacf599f8f6d6aca1` before application edits. Matching captures cover desktop queue new/reviewed/applied/picker, bulk groups/selected rows, and 320/390px long-tag builder/accepted request, ready/pending/incomplete playlists, song picker/error, vocabulary and destructive confirmation. `.local/ui/capture.mjs` uses the existing synthetic fixtures, mocks every API route, aborts non-local requests, and waits for meaningful rendered states. Stable-error replacements and empty-vocabulary supplements were subsequently rendered from a source-only snapshot of the same baseline commit; the supplemental manifests distinguish these from the initial captures. The subsequent toast-collision repair has focused `.local/ui/toast-before/` (78a1b817) and `.local/ui/toast-after/` evidence at 1280×720/600, with commit provenance; the original c96 design baseline stays intact. No actual Spotify metadata or credentials enter these artifacts.

Browser regression assertions measure resolved text/background colours, text opacity, enabled field boundaries and placeholders without pinning exact CSS colours or screenshot goldens. They cover normal, selected, applied, picker, failure and confirmation states, plus stable navigation emphasis before/after arrival review and nonintersecting home/account targets at 320/390px. Existing reflow, visible focus, modal, keyboard/IME, frozen selection and undo tests remain delivery gates. Typecheck, frontend tests, production build and formatting checks accompany the browser suite. The orchestrator independently runs `scripts/check`, the rendered critique, pinned Standards/Spec review, exact-head CI, deployment and redacted live verification.

Actual phone keyboard behavior and the under-one-minute phone flow, familiar-song tagging at roughly 3–5 seconds per song, and actual profile/search hiding remain **pending human product acceptance**. Synthetic emulation and successful publication commands do not establish those outcomes.

# Spotify Plus visual design

The redesigns for [issue #63](https://github.com/CarterKFalkenberg/spotify-plus/issues/63) and the guided workflow overhaul in [issue #67](https://github.com/CarterKFalkenberg/spotify-plus/issues/67) establish a compact music workspace. It takes cues from the clarity of Apple software and Spotify's emphasis on the collection, while retaining its own navigation, composition and typography. The [product brief](PRODUCT-BRIEF.md), [accepted decisions](DECISIONS.md), and [everyday flows](UX-FLOWS.md) define behavior. This is a frontend redesign, not a change to Spotify contracts, tagging semantics or playlist guarantees.

## Composition

The desktop application uses a restrained graphite or neutral navigation rail. Account access and appearance sit in the header; sync status stays above the current task. The rail does not become a second dashboard. On phones, five compact bottom destinations keep playlist composition, playlists, new arrivals, library and vocabulary accessible without consuming the top half of the screen. Account access remains a named disclosure; mobile arrival tagging remains a native modal sheet.

Each surface has a different composition serving its task:

- **Queue:** large square artwork and track identity occupy one column. The other is a tagging desk: current tags, immediate-save reassurance, autocomplete, and nine keyboard slots in a compact three-column grid. Previous/Next/Skip form a separate navigation group; Open in Spotify remains visible with track identity; artist and help tools live in Song actions. Queue settings holds ordering. Count-up session feedback remains in the heading. No playback controls or invented listening state appear.
- **Library:** edge-aligned collection rows, with artwork and song identity leading metadata, tags and editing. Grouped artist/album/decade results become compact ledger rows with tagging controls beside identity, rather than independent cards. Songs/Artists/Albums/Decades form an explicit browse switch. Search and Untagged stay visible; membership, sorting and facets expand under Filter & sort. Group selection opens one shared bulk editor. Pages contain at most 12 groups or 30 songs, with paging beside result counts and below the list. Frozen selection, tri-state add/clear, and changed-only undo retain their existing handlers and sticky dock.
- **Builder:** Choose tags → Review songs → Name & keep. All of starts the query; a named refinement control reveals Any of and None of. Count and duration remain visible throughout. Review uses a bounded list with one exclusion summary and inline unavailable reasons. Back preserves drafts; Playlist details leads to editable name, visible retention, concise expiry/link-access copy and further Spotify disclosures. The ordinary phone step keeps its task and primary action visible. Longer content and open suggestions use normal scrolling.
- **Playlists:** a collection ledger aligns name/query, status/count, expiry and creation date. Open in Spotify is the principal action; each playlist owns its Manage disclosure and retention draft. Healthy Ready badges are omitted. Pending, incomplete and removal states retain literal text and separate visual treatment; Ready never means independently proven profile/search hiding.
- **Vocabulary:** dictionary rows pair the tag string and usage/last-use metadata with contextual management and explicit merge-source selection. Tags stay flat and uncolored. Rename, merge, previewed impact, deletion confirmation and undo continue to use the existing domain operations.

Connection, account, policy, empty and error views share the same typography, materials and controls. The connection screen explains the actual workflow without a marketing hero, numbered feature ceremony, decorative gradients or fake player imagery. Destructive actions stay in named native confirmation dialogs.

## Appearance and shared controls

Appearance is a device preference, exposed through a compact icon-and-label **Appearance** disclosure on every page, with named radio choices and visible selected state. Its choices are **System**, **Light**, and **Dark**. The initial choice is System. The choice persists under `spotify-plus-theme` in local storage when available, follows changes from another tab, and responds to OS appearance changes only while System is selected. Invalid or unavailable storage falls back to System; an explicit current-visit choice still works when persistence is unavailable.

A small blocking `appearance.js` bootstrap resolves the preference before application styles and React render. The React control consumes the same resolver, avoiding two independent implementations. It sets the document theme, native `color-scheme`, and browser theme-color together. This application is client-rendered; there is no server hydration state to disagree with the selected appearance. The bootstrap also avoids rendering the wrong appearance while session state loads.

Light uses a cool neutral canvas, white work surfaces and near-black type. Dark uses graphite canvas, slightly raised charcoal surfaces and warm-white type. Supporting text remains readable rather than decorative. Artwork supplies the broad color. Green is reserved for principal actions, active navigation, connection indicators and the quiet new-arrivals marker; tags never acquire color identity.

`--control-line` identifies enabled fields separately from decorative `--line` dividers. All inputs, selects, placeholders and supporting text must meet the existing rendered contrast assertions. Focus uses a visible three-pixel outline independent of hover and selected states. Applied tags, selected autocomplete options, bulk tri-state text, checked boxes and saved/undo feedback communicate state beyond color. Native disabled semantics and busy states remain intact. Reduced-motion preferences suppress motion.

## Evidence and verification

Before/after proof uses synthetic fixtures only. Real Spotify names, library metadata, images and credentials never enter screenshots or model context. Matching baseline and final captures, exact source provenance and explanations are published with the PR and linked in the delivery response. The [detailed captioned proof gallery](design/proof/README.md) includes 22 comparisons and their source/hash manifest under `docs/design/proof/`.

Browser checks continue to measure resolved text contrast, enabled field borders, placeholder contrast, focus, reflow, modal behavior, keyboard/IME safety, selection/undo and navigation hierarchy. Both palettes cover authenticated library, bulk selection, builder suggestions, playlist states, queue applied tags and suggestions, vocabulary and destructive confirmation. Geometry checks cover desktop account/appearance separation, phone task and primary-action clearance, focused sheet suggestions, group Browse targets, and the separate saved-feedback row at 600px and 720px desktop heights.

The sticky bulk editor bounds its scrolling controls while preserving visible Undo feedback. Group tagging and all-matching tagging share the same selection editor and separate feedback row. In-flow picker menus remain stable through a pointer press: closing the menu on blur used to shrink the sticky editor between pointerdown and click, losing the outside button's click. The picker now closes after that gesture finishes, while keyboard blur closes immediately; cancellation, frame and document-listener cleanup are explicit. The frozen-revision reselection regression continues to require the owner's actual click before adopting a refreshed filter result. Appearance checks cover System/OS changes, explicit preferences, reload/navigation persistence, native color-scheme and unavailable/invalid storage. Existing behavior assertions remain acceptance gates; changes to markup require equivalent behavior and accessibility evidence, not weaker tests.

The orchestrator independently owns full checks, visual critique, pinned Standards/Spec review, exact-head CI, deployment and redacted live verification. Actual phone keyboard behavior and the under-one-minute phone flow, familiar-song tagging at roughly 3–5 seconds per song, and actual profile/search hiding remain **pending human product acceptance**. Emulation and acknowledged publication commands cannot establish those outcomes.

## Guided task composition — issue #67

The October 21 overhaul follows the user's [accepted workflow direction](DECISIONS.md#guided-everyday-workflows--october-21-2026). The three builder stages are Choose tags, Review songs, and Name & keep. Each stage exposes one primary action and Back preserves the draft. All of remains the starting point; an explicit refinement control reveals Any of and None of, including a count when populated refinements are collapsed. The live count and duration remain visible throughout. Review uses the same cached preview and exclusions; creation still validates the current preview revision and persists the exact request before transmission. Stage transitions never submit the create form. A successful request offers Make another playlist, resetting the draft only after the prior exact intent is confirmed. Narrow or enlarged content can scroll instead of being clipped.

Desktop library browsing has explicit Songs, Artists, Albums, and Decades destinations. Phones retain the brief’s lite song list/search and arrival-sheet tagging, without group browsing or bulk controls. Requests are bounded to 12 groups or 30 songs, with Previous/Next page controls. Page history changes only after a successful response; rapid clicks cannot stack requests and a failed target remains retryable. Changing a filter or browse mode resets paging; all-matching selection continues to capture the entire matching filter and its revision, rather than the visible page. Group rows expose Tag songs and Browse songs, opening a single shared selection editor instead of mounting a tag search on every group. Artwork is contained and linked to Spotify; placeholders describe unavailable artwork rather than inventing an artist portrait. An explicit artwork-pending response enables current-page refresh only while active and visible, every three seconds for at most one minute; a Check artwork action restarts that bounded wait. Known unavailable artwork stops polling. This does not change semantic library/annotation revisions.

The queue retains large art, immediate tagging, quick slots, and a dominant Next. Queue settings and Song actions disclose secondary controls. Open in Spotify has one explicit visible link. Healthy playlist rows show artwork, identity and expiry, Open in Spotify, and a per-playlist Manage disclosure; retention drafts belong to that playlist. Incomplete, blocked, removing, and ambiguous-request states retain literal explanations and retry actions. Healthy Ready badges are omitted. Tag rows retain one contextual edit entry and usage count.

Appearance now uses an icon-triggered, named disclosure with System, Light and Dark radio options. The preference resolver, pre-paint bootstrap, persistence, cross-tab and OS behavior remain unchanged. Both palettes share the same hierarchy and accessible selected states.

Header utilities participate in normal wrapping layout, and bottom navigation items wrap into additional rows when enlarged text needs space, preserving whole words and the ordinary five-item row. A ResizeObserver measures the actual navigation height to reserve document scroll space and position sticky builder actions, including when text grows. Browser regressions pre-collect every HTML element's computed font size, double those sizes, and verify the measured ratio, painted label containment, unbroken word ranges, separate header targets, horizontal reflow and reachable stage actions at 320/360 pixels in both themes. This synthetic text enlargement is distinct from native browser zoom and an actual phone keyboard; a separate 360×480 viewport check verifies scrolling from focused input and suggestions to the next action.

Verification evidence is collected after the candidate is rendered and independently critiqued. Source changes or a passing test run alone are not visual acceptance, actual phone acceptance, or proof of Spotify publication hiding.

## Spotify artwork attribution

The shared footer links the full official Spotify logo to Spotify and labels the music source. It uses the unmodified `Full_Logo_Black_RGB.svg` and `Full_Logo_White_RGB.svg` assets from Spotify's [official full-logo package](https://developer.spotify.com/images/guidelines/design/2024-spotify-full-logo.zip), downloaded October 21, 2026. The files are retained as `app/public/spotify-logo-black.svg` and `app/public/spotify-logo-white.svg`. Black appears on the neutral light surface and white on graphite, at 88 CSS pixels wide with surrounding space, following the [Spotify design guidance](https://developer.spotify.com/documentation/design). The app does not tint or redraw the logos. Individual artwork remains contained and linked to its Spotify entity; the footer supplies consistent brand attribution. These public brand assets are separate from private Spotify metadata and synthetic QA imagery.

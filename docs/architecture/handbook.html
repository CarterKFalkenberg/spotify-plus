01 · System and boundaries

One product, three execution environments

Spotify owns library membership. PostgreSQL owns your tags and intended playlist work. Spotify stores the resulting playlists. The browser lets you express intent and observe progress; it does not keep background work alive.

Synchronous path

Search, facets, tag edits, undo and query previews go through the API to transactional SQL. A returned mutation result reflects committed application state.

Durable path

Sync, playlist writes, expiry and backups become database jobs. A successful “accepted” response can precede completion of the Spotify operation. Polling displays the eventual result.

The Cloudflare Worker is a gateway, not the background worker. Supabase’s jobs function runs a bounded batch and exits. PostgreSQL is both the state store and the durable queue. There is no Redis, Cloudflare Queue, permanent Node server, playback SDK or runtime AI integration.

Sources: proxy/worker.ts · API wiring · jobs wiring · hosting design.

03 · Login and security

Spotify login becomes an opaque app session

account_id is durable owner identity. The configured legacy user ID supports the initial owner check; it is not the permanent binding. Supabase Auth is not the product login. An app session contains an opaque cookie, while the database stores its hash. The API checks that session against the account’s current epoch, so stale work cannot act for a later connection.

BoundaryEnforcement
Browser → proxyAllowlisted routes/methods; JSON POSTs require exact app Origin and a body of at most 16 KiB. Only a small header allowlist is forwarded.
Proxy → APIFixed Supabase origin; server proxy secret replaces any client-supplied secret. Private responses are no-store; cookies and OAuth redirects survive.
API → product actionOwner session, epoch and parsed input. OAuth has separate state/PKCE checks. Bootstrap has its own secret and one-time consumption rules.
Scheduler → jobsA distinct cron secret. The public Worker does not expose the jobs or bootstrap paths.
Functions → SQLServer service credentials; anonymous/authenticated clients do not get table/RPC access. Definer RPCs use explicit search paths and owner/lease checks.
Function gatewaySupabase JWT checks are disabled for these handlers because their own session/service authentication is authoritative. This does not make the handlers anonymous.

Refreshing and reconnecting

OwnerTokens claims a SQL refresh lease, decrypts server credentials, refreshes if needed, then stores any rotated refresh token. Token versions prevent concurrent 401 responses from refreshing the same credential twice. The original authorization date anchors the estimated six-month deadline; refreshing does not reset it. invalid_grant or an ambiguous rotation can require reconnect. Cached browsing, annotation edits and annotation backups can remain available to a valid existing session while Spotify-dependent work waits.

04 · Data model

Permanent annotations, disposable metadata

A track has two lives. Its cached Spotify metadata can disappear after removal. Its annotation identity and tags survive until disconnect. The join key is an HMAC of the Spotify track ID using a random per-account key; that key is stored encrypted under the runtime annotation wrapping key.

Supporting recordsWhy they exist
account / credentials / sessions / oauth_statesSingleton owner, connection epoch, encrypted grants, opaque-session hashes and one-time OAuth state.
library_state / sync_runs / sync_seenInitial-completion gate, revision counters, stable-pass comparison and resumable offsets.
page_cursors / playlist_cursorsOpaque bounded paging state tied to query/filter and revision; stale cursors cannot silently page a changed result set.
vocabulary_changes / vocabulary_deletesManagement receipts, deleted tag identity and session undo.
jobs / runtime_health / spotify_pacing / cron_dispatchesLeases, retries, runtime revision, scheduler evidence and shared API cooldown.
annotation_backupsSnapshot identity, epoch, retention and purge registry for private Storage targets.

track_tags.present and version preserve enough history to detect later edits during Undo. Tags use immutable UUIDs; names are labels. Renaming a tag therefore does not invalidate stored query identity, and merging can rewrite query leaves transactionally.

05 · Import and reconciliation

A page offset is progress, not a snapshot

Spotify’s saved-library pages can change while the app walks them. An item added or removed near the front shifts later offsets. The importer therefore cannot conclude that “we reached the end” means “we saw the whole library.”

Two consecutive valid full passes must match on track identity and liked-at membership. Equal totals alone miss a swap. Writes within a page are idempotent and transactional with the resume offset, so a worker restart does not lose the relationship between what was stored and where it should continue.

TriggerBehaviorGuarantee
First connectionEnqueue full import automatically.Generation stays disabled until stable completion; tagging works on imported tracks.
App openFirst-page/total probe, debounced to 15 minutes.A cheap hint; matching head/total cannot prove no change.
Sync nowRequest a full verified walk.Detects changes beyond the head.
Daily backstopMaintenance schedules a full sync after 24 hours.Continues without browser activity while hosting is healthy.

The “new” badge uses explicit acknowledgement. “New since last sync” uses additions in the latest completed run; these are different concepts. Null, unavailable or unusable items are handled explicitly, and items without a valid playable track URI cannot become playlist targets.

For a synthetic 3,000-song library, a 50-item page size means 60 requests per pass and at least 120 across two matching passes. This is request arithmetic, not a latency promise. Continuous library mutation can keep verification unsettled.

06 · Tagging and undo

Freeze the target; record only what changed

The queue is optimized for repeated small decisions. The library browser is optimized for one decision across many songs. Both eventually use the same transactional annotation model.

RuleReason
Some → all on Add; explicit Remove clearsTri-state selection must not interpret a mixed selection as a toggle that deletes existing tags.
Same assignment is a no-opBulk add should not create duplicate edges or inflate the Undo journal.
Changed-only, version-checked UndoIf you edit a track later, Undo of an earlier batch must not overwrite that newer decision.
Normalized identity; first display spellingNFC, whitespace collapse and case-insensitive matching prevent accidental duplicates while preserving accents and punctuation.
Rename preserves UUID; merge rewrites referencesPlaylist queries should keep meaning when the vocabulary is gardened.
Delete leaves explicit deleted-tag semanticsA missing query leaf must not silently broaden a playlist query.

Browser selection can be explicit IDs or “all matching.” The server resolves the latter against a revision at mutation time under its lock. This is separate from the queue’s browser-side frozen list. New sync arrivals cannot silently change the target halfway through a committed tag operation.

07 · Queries and previews

The UI builds a tree; SQL evaluates it

The mobile builder emits three buckets, but the stored representation is a versioned tree with tag, and, or and not nodes. Leaves contain tag UUIDs, not names. This keeps query evaluation independent of the present builder layout.

Preview costs zero Spotify requests. It is local database evaluation over the cached library. Create requires a completed initial sync and freezes the ordered target in SQL. A changed revision invalidates stale assumptions rather than silently turning an old preview into a different result.

Preview distinguishes matched = playable + excluded: unavailable matches can appear in preview pages, but only playable targets can be generated. SQL validates every referenced tag before evaluation, including leaves under NOT or short-circuited branches; a deleted leaf rejects the query with unknown_tag.

After creation, tag edits do not update the playlist automatically. Regenerate explicitly reevaluates the stored query, creates a new target snapshot and replaces the contents of the same Spotify playlist. Deleted-tag feedback remains visible; label lookup failures are not proof a tag was deleted.

Sources: Builder · query validation · query evaluation · create transaction · label resolution.

08 · Playlist lifecycle

Remote side effects need evidence before completion

There are three related identities: the app playlist UUID, the Spotify playlist ID, and an operation UUID/job. The app stores request receipts to deduplicate a repeated product intent, and operations store the exact target that a worker must achieve. Neither mechanism makes Spotify POST requests inherently idempotent.

Before each resumed write, the runner rechecks the lease and remote state. A lost append response may mean the chunk already exists. Reading ordered contents and comparing the target prefix prevents a blind append retry from duplicating it. A mismatch can require replacement or yield a remote-change failure; a persisted offset is never enough authority to replay a POST.

ActionStored/remote effect
CreateFreeze query target; create tracked noncollaborative playlist, populate, disclose retention, request unpublished state.
RegenerateReevaluate tags, replace membership in the same playlist, reset expiry; preserve current Spotify name and non-Tagger description text.
Extend / pin / unpinUpdate retention/disclosure through a serialized operation. Pinned has no expiry date.
Delete now / expireGuarded removal from Your Library; confirm via containment and the current-user playlist collection.
ReconcileNotice external removal, confirm ownership/state, refresh publication command without rewriting outside description text.

Retention uses America/New_York calendar dates. A month is a calendar month with month-end handling, not 30 × 24 hours. A playlist is valid through its expiry date; scheduled cleanup occurs afterward. Metadata descriptions disclose that regeneration overwrites manual track edits.

“Ready” has a specific software meaning. Ordered content and disclosure are verified and the fixed public:false/collaborative:false command is acknowledged. Repository evidence records contradictory publication readback; actual profile/search hiding remains unverified product acceptance. Removal means absence from Your Library, not destruction of Spotify’s object or link.

09 · Workers and recovery

The database remembers; a function takes a turn

The shared drain caps its budget at 80 seconds, claims at most 20 jobs, and stops starting more claims when fewer than 50 seconds remain. Claims request 100-second leases. Feature runners also check deadlines and lease/epoch fences. Those are ceilings and safety margins, not promises that every invocation performs 20 jobs or runs for exactly 80 seconds.

The API can call the same drain using EdgeRuntime.waitUntil after relevant actions. That reduces perceived delay. It is opportunistic; durable rows and later cron ticks recover if the invocation is terminated.

11 · Backups and disconnect

Protect annotations without reviving a disconnected account

Backups contain live tag identities/names and present HMAC-to-tag edges. They exclude raw Spotify IDs, cached metadata, tokens, sessions, playlist queries, pending jobs and undo journals. A daily copy is encrypted with AES-GCM and bound to owner, epoch and snapshot identity; the three latest successful daily copies are retained.

Each snapshot uses a unique private bucket and one ciphertext object. Creation intent permits one bucket-creation attempt for an identity. Lost acknowledgements are reconciled instead of replayed indiscriminately. Epoch and lease checks fence uploads; deleting the never-reused bucket also prevents a stale upload from finishing after disconnect. Failed target cleanup blocks allocation of more daily targets, avoiding an unbounded accumulation during an outage.

The backup key link is a hash of the current encrypted annotation identity key; the backup does not contain that key. Restore therefore requires the same current owner/epoch/key context and cannot recover a disconnected account into a new epoch.

Restore is an operator-only whole-annotation replacement guarded by current owner, epoch, key linkage and expected revision. It cannot recreate credentials, sessions or old jobs. Concurrent edits reject a stale restore; a concurrent disconnect prevents resurrection. Real restore requires explicit human intent; synthetic restore proofs are separate.

Disconnect leaves existing Spotify playlists in place and stops their automatic cleanup. A minimal keyed owner fingerprint remains to preserve the single-owner binding. The owner can revoke the Spotify grant on Spotify’s account Apps page. Application-controlled deletion can be verified; a successful API deletion does not prove physical byte erasure across provider-internal retention systems.

Sources: backup operations · backup runner · Storage adapter · restore tool.

The dangerous-looking scope has a narrow code boundary. The grant includes user-library-modify, but every saved-library write is rejected except DELETE /me/library with validated, app-managed spotify:playlist: URIs. Track like/unlike, other entity types, mixed lists and unmanaged playlists must fail before dispatch.

The exact requested scopes are user-library-read, playlist-read-private, playlist-modify-private, playlist-modify-public and user-library-modify. There are no profile, player or follow scopes. Grant breadth is not authorization for every endpoint it could technically permit.

The adapter also validates responses and pagination URLs. It tolerates limit:0 only for the observed empty first terminal playlist-items page, and decodes description escapes once. These narrow accommodations avoid turning provider irregularities into permissive parsing.

14 · Setup and delivery

Build tools are separate from runtime services

Node 24 runs Vite and local orchestration. Deno runs backend checks and Supabase functions. Docker hosts disposable local database/Supabase tests. Wrangler deploys assets/proxy; Supabase CLI applies migrations and deploys functions. GitHub Actions verifies synthetic behavior without production secrets.

# Prerequisites: Node 24, Deno, Docker, Supabase CLI and Wrangler
# See the repository docs/SETUP.md for installation and configuration.

# In your own isolated codex/... worktree
npm ci
npm run dev                 # UI dev server; browser tests mock API traffic
sh scripts/check           # complete synthetic check pipeline
node scripts/check-supabase.mjs  # disposable stack; coordinate its ports

# Read the operator guide before running live stages
# node scripts/verify-stage.mjs <stage>
# Stages can mutate registered disposable Spotify playlists.

A Vite dev server alone is not a locally authenticated full-stack product. OAuth callbacks and same-origin proxy behavior need the documented setup. New worktrees share the ignored .local directory through a symlink, never by copying secrets. Do not regenerate existing encryption keys when reconnecting or deploying.

16 · Glossary

The vocabulary behind the diagrams

Epoch
A connection generation. Changing it invalidates old sessions/work authority and prevents a stale worker from resurrecting disconnected data.
Lease and fence
A temporary claim on a job plus a token checked before continued work. A fence rejects a worker whose lease or account generation is no longer valid.
Checkpoint
Committed progress used to resume work. It does not prove a timed-out remote write failed or make a POST safe to repeat.
Revision
A counter describing application data changes. It guards cursors, previews, mutations and restores from stale assumptions.
Snapshot playlist
A frozen ordered membership set. Future tag edits affect only future generation or explicit regeneration.
Spotify snapshot ID
A provider playlist-version marker used during remote verification. It is distinct from the app’s stored target snapshot.
HMAC track key
A stable pseudonymous annotation key derived from Spotify track identity and the account’s secret key. It allows metadata deletion without losing tag associations.
RPC
A server-invoked PostgreSQL function exposed through PostgREST. A single RPC can lock rows, validate inputs and commit several related changes atomically.
Reconciliation
Read external reality and compare it with intended state before deciding what to do next, especially after an uncertain write.
Publication acknowledgement
Spotify accepted a request to hide profile/search publication. In this project that is software evidence, not independent proof of the visible outcome.
Software readiness versus product acceptance
Automated checks and live evidence can establish software readiness. Actual phone speed, familiar-song tagging pace and the required Spotify publication outcome remain separate acceptance questions.

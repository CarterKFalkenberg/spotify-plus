# Managed snapshot playlists

Issue [20](https://github.com/CarterKFalkenberg/spotify-plus/issues/20) implements the playlist backend within the full core-loop scope. This document describes software behavior; it does not claim live playlist or phone acceptance.

The authenticated API accepts an explicit retention (`month` is the displayed default), request UUID, and library/annotation preview revision. One transaction locks the owner and library state, verifies the complete query and stable initial import, and freezes playable matches in newest-liked order. The stored versioned query remains complete even when its rendered Spotify description is shortened. Saved-library writes remain confined to guarded removal of managed playlist URIs.

A mutation returns a durable pending intent with HTTP 202. It immediately starts the existing leased job drain through Supabase's [background-task API](https://supabase.com/docs/guides/functions/background-tasks). That invocation claims at most 20 jobs and has an 80-second budget. It does not invoke another function or keep a permanent worker alive. The existing cron entrypoint schedules expiry and reconciliation and recovers interrupted work. The browser must poll the playlist list; acceptance of an intent never means Spotify creation or completion has been confirmed.

Creation is private and non-collaborative. Before its first create request, the worker stores a durable marker. A lost response causes a complete current-user playlist scan for that marker, plus owner/private checks. If creation remains ambiguous, the operation stays incomplete and Retry repeats reconciliation, never an unproven create POST. Append recovery reads ordered remote items, including unavailable positions, before deciding whether to append a verified missing suffix or rebuild. Checkpoints record read progress; they do not make POST requests idempotent. Ready requires confirmed ordered contents and description.

Pin, Unpin, Extend, Regenerate, Delete and cron cleanup share the same expected-revision, epoch and lease fences. A repeated request UUID with the same intent returns its original acknowledgement before checking stale revisions; changed intent conflicts. Regenerate re-evaluates the stored query, freezes its new target, preserves the current Spotify name and exact non-Tagger description text, and resets the clock only on confirmed completion. Retry retains the original target. The description discloses snapshot membership, overwritten manual edits and expiry removal. Accepted punctuation in tag names is escaped inside the managed block so it cannot terminate the block.

Dates use America/New_York calendar arithmetic, clamp month ends, and remain valid through the displayed date. Cleanup begins on a later local date. Both explicit Delete and due expiry can supersede an incomplete known-ID write after its lease is no longer live. The old operation is cancelled and fenced before disposal begins. Cleanup continues retrying through provider outages; five transient failures do not abandon removal. It uses only `DELETE /me/library` with managed `spotify:playlist:` URIs, then confirms absence through both contains and current-user playlists. An accessible playlist object, a 404 or a 403 alone does not confirm removal. Daily reconciliation also retires externally removed playlists. The last-cleanup timestamp advances only when the whole due pass is clear; pending or blocked disposal remains visible.

Synthetic coverage includes module/API/shared-worker tests, a disposable PostgreSQL suite with concurrent requests and lifecycle races, and PostgREST assertions under active pg-safeupdate. The latter exercises real RPC projections, immediate drain, regeneration, pinning, stale requests, permanent description failure, repeated removal outages and natural scheduled expiry. Production deployment, real Spotify proof and final phone/tagging-speed acceptance remain orchestrator/user gates.

The scheduler retains only pg_net request IDs and dispatch timestamps in private `app.cron_dispatches`, deleting records older than seven days. Its HTTP timeout is 90 seconds so the bounded worker can return an observable response; the primary [pg_net contract](https://supabase.com/docs/guides/database/extensions/pg_net) defines this integer millisecond timeout and returned request ID. An operator can correlate a genuine post-deadline cron dispatch with `net._http_response` and the expiry operation's finished job. API/background health timestamps alone do not prove scheduled execution. This record stores no request body, authentication values or Spotify data.

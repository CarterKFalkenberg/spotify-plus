# Usability overhaul research — October 21, 2026

Research for [issue #67](https://github.com/CarterKFalkenberg/spotify-plus/issues/67). Inspected source at `34b6ac775e4aa2404f4198cf50488e589c09eae7`; this is a source-based critique, not a measured usability study or live Spotify API proof. The user reports too many equally prominent controls, unclear library purpose, excessive scrolling, an unattractive appearance control, a builder that should guide them through steps on a phone, and playlist cards without artwork. Those observations motivate the proposals; citations do not establish that any particular redesign has succeeded.

The [brief](../PRODUCT-BRIEF.md), [decisions](../DECISIONS.md), and [plan](../PLAN.md) retain priority: desktop tagging speed, first-run bulk groups, mobile generation, all three query buckets, preview before creation, flat tags, and complete playlist lifecycle stay in scope. Research performed no Spotify calls, content inspection, deployments, or external mutations. Sources were checked October 21, 2026.

## Evidence from primary design sources

| Source | Supported observation | Application to this product (design judgment) |
| --- | --- | --- |
| [NN/g: Cognitive load](https://www.nngroup.com/articles/minimize-cognitive-load/) | Unnecessary visual information consumes attention; familiar patterns, useful defaults, and displaying information instead of requiring memory reduce incidental work. | Stop explaining background machinery in normal screens. Use song identity, chosen tags, and the next action as the dominant content. |
| [NN/g: Progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) | Prioritize frequently needed options and disclose specialized controls on request; staged disclosure can sequence a task. | Move queue setup and playlist maintenance behind clearly named secondary controls. Keep daily accelerators visible. |
| [GOV.UK: Question pages](https://design-system.service.gov.uk/patterns/question-pages/) | Ask only necessary questions; begin by structuring a form around one thing per page. | Use three builder stages: choose tags, review songs, name and retention. Preserve state when moving backward. This is an adaptation from public-service forms, not a universal rule that every field needs a screen. |
| [Material buttons](https://m2.material.io/develop/web/components/buttons/) and [first-party Material component documentation](https://github.com/material-components/material-components-android/blob/master/docs/components/CommonButton.md) | Button styles convey different levels of emphasis; the former recommends one prominent action in a layout. | Use one dominant next action per task surface. Open in Spotify should dominate playlist maintenance. A primary style on every button destroys this distinction. |
| [NN/g: Data tables](https://www.nngroup.com/articles/data-tables/) | Browsing data involves finding, comparing, inspecting/editing, and acting on records. Consistent rows support scanning and comparison; search/filter/sort address different ways of finding records. | Separate browsing groups from editing a selected group. Preserve compact song rows and bulk operations; decorative giant cards are not an automatic improvement. |
| [Apple HIG: Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode) ([official Markdown](https://developer.apple.com/design/human-interface-guidelines/dark-mode.md)) | Apple recommends respecting system appearance and avoiding app-specific settings; both appearances must remain legible. | Preserve existing System/Light/Dark behavior for this web app, but demote the chooser into a compact labeled secondary control. This deliberately adapts, rather than literally follows, Apple's native-app recommendation. |
| [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) | At 320 CSS pixels wide, ordinary vertical content must remain usable without two-dimensional scrolling or lost functionality. | Fit the ordinary builder stage on a phone, but allow vertical overflow when text grows, keyboard opens, or errors appear. Never satisfy a screenshot by clipping controls. |
| [W3C: Focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) | Author-created sticky layers must not entirely hide the focused control. | A bottom Next/Create bar needs reserved space, scroll padding, and keyboard checks. Prefer fully visible focus even though the AA minimum permits partial obstruction. |
| [W3C: Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | The AA minimum is 24×24 CSS pixels, with defined exceptions including spacing. | Target approximately 44×44 for frequent phone actions as a product usability target; do not misstate 44 pixels as this WCAG criterion. |

## Source observations and specific redesign proposals

### Queue

**Observed:** `app/src/Queue.tsx` renders order selection, quick-slot customization, previous/next/skip, arrival acknowledgement, Spotify open, artist browsing, remove-last-tag, help, and undo around the same track. It already distinguishes Next with a primary class and hides slot pin controls outside edit mode. The problem is not literally an absence of hierarchy; it is the aggregate number of competing decisions.

**Proposal:** Center track art/identity, current tags, persistent tag input, and nine quick slots. Keep Next dominant, previous/skip secondary, and undo adjacent to save feedback. Put order and slot configuration under Queue options; place artist jump, remove-last, and shortcut help under a labeled More actions control. Keep Spotify open directly discoverable. Preserve every shortcut, typing/IME behavior, session count-up, skip-to-tail semantics, and immediate saving. Do not hide quick slots to achieve a low button count: they are the throughput feature, not clutter. Mobile retains the arrival-card/sheet flow.

### Library

**Observed:** `app/src/Library.tsx` has search, membership, untagged, sort, group mode, queue action, and facet disclosure. Each group mounts a monogram, title/count, TagPicker, Select group, and Browse songs. A large collection multiplies editors before the user has chosen anything. Current requests use `limit: 50`; the source's `180` is a debounce duration, not a list limit. Do not turn the user's long-list complaint into a fabricated implementation fact.

**Proposal:** State the purpose: find songs and tag many at once. Offer clearly distinct Artists / Songs views with album and decade grouping retained as secondary choices. First-run artist groups remain ordered by size. Use compact artwork-led groups with counts and one obvious group action; reveal a single contextual bulk editor after choosing a group. Keep search and Untagged visible, summarize active facets, paginate groups with an explicit next-page control, and retain selection of all matching songs across pages. Group paging must not silently constrain bulk selection to visible rows. Album covers must not masquerade as artist portraits. Use the correct group noun for album/decade labels instead of universal “songs by”.

### Builder

**Observed:** `app/src/Builder.tsx` simultaneously lays out live query feedback, three independent bucket pickers, a preview disclosure, name, retention, create, and substantial explanatory copy. The name and retention are present before a query has meaningful results. Collapsing the preview alone does not create a guided flow.

**Proposal:** Explicit progress: **1 Choose tags → 2 Review songs → 3 Name & keep**. Step one preserves All of / Any of / None of with plain-language explanations and current count/duration. Optional buckets can disclose individually, but their entry controls and populated values must remain obvious. Step two shows a bounded scrollable preview, total, duration, and exclusions; zero matches has a useful correction path. Step three shows an editable suggested name, visible retention, compact query/result recap, and Create. Keep hiding/link-access limitations and expiry implications discoverable before creation. Back preserves values; query/library changes invalidate stale preview; a pending ambiguous create retains its saved request and cannot be resubmitted as a new intent. Do not require reviewing every song or ticking an artificial confirmation box.

A wizard increases navigation cost. It is justified here by the user's explicit request and small phone target, not by a claim that wizards always outperform forms. Use meaningful Next labels (“Review songs”, “Playlist details”) and concise progress. Returning to an earlier stage must be cheap.

### Playlists

**Observed:** `app/src/Playlists.tsx` shows a Ready pill on healthy cards, raw query punctuation, creation/expiry details, several actions, a global Extend/Unpin retention setting, and cleanup status. The card has no artwork. “Ready” is an internal success state that adds little when an Open action is already available. The source does not justify assuming every playlist whose name contains “test” is disposable.

**Proposal:** Artwork, name, song count, and expiry identify each playlist; Open in Spotify is the dominant action. Put Extend, Pin/Unpin, Regenerate, and removal under Manage, with retention chosen in the affected playlist's context. Keep urgent blocked/incomplete/removing states visible and actionable; hide only routine healthy status. Show stored query chips and created date in the card's details. Healthy cleanup belongs in quiet supporting information; delayed or blocked cleanup stays conspicuous. Preserve request ambiguity and retry semantics. Never rename, hide, or remove actual playlists merely to make test-looking names disappear.

### Tags

**Observed:** `app/src/Vocabulary.tsx` already has search, sorting, counts, last-used, Manage, a merge-selection mode, and confirmation previews. A repeated Manage label and “Tag vocabulary” framing make it feel like administration rather than the user's working words.

**Proposal:** “Your tags”, a concise purpose sentence, searchable compact rows, and a clearly clickable tag name leading to one edit sheet. Keep usage counts prominent and last-used secondary. Rename is the default edit; Merge and Delete reveal their impact before confirmation. Keep unused tags available without a large warning area. For merges, retain exact distinct-track union counts, target choice, stored-query safety, and session undo. Do not add categories, color coding, descriptions, or tag hierarchy.

### Appearance

**Observed:** `app/src/Theme.tsx` already stores System/Light/Dark, listens to system changes and cross-tab storage, and tolerates storage failure. The complaint is about presentation, not missing preference support.

**Proposal:** Replace the prominent select with a compact Appearance disclosure in the utility area, with three named options and visible selected state. Avoid an unlabeled cycling sun/moon icon: three states are difficult to infer. Preserve pre-paint theme application and existing persistence. Do not tint, darken, or crop Spotify artwork to make a theme look better; Spotify's more specific artwork rule overrides generic Apple image advice.

## Spotify artwork: documented contract and unresolved assumptions

1. [Get Artist](https://developer.spotify.com/documentation/web-api/reference/get-an-artist) documents `GET /artists/{id}` and an `images` array ordered widest first. [February changes](https://developer.spotify.com/documentation/web-api/references/changes/february-2026) explicitly retain that route but remove bulk `GET /artists`; artist followers/popularity are removed in development mode. Fetch by the known library artist ID, not a name search. Do not assume simplified artist objects attached to tracks contain portraits.
2. [Get Playlist Cover Image](https://developer.spotify.com/documentation/web-api/reference/get-playlist-cover) documents `GET /playlists/{playlist_id}/images`; February's retained list includes it. This is a read. The separate upload route is unnecessary for showing Spotify art and must not expand write scope.
3. [Get Playlist](https://developer.spotify.com/documentation/web-api/reference/get-playlist) documents an empty or up-to-three image array and warns that returned image URLs expire in less than a day. A once-saved URL is not durable artwork. Refresh metadata on a bounded schedule or controlled demand, and tolerate missing/failed images. The reference's generic owner fields must not replace the project's `account_id` identity rules.
4. The artwork endpoint's policy notes require original visual content, a link to the applicable Spotify entity, and Spotify attribution. Use original remote image URLs with containment rather than arbitrary cover crops, overlays, collages, or rehosting. Keep real content out of model prompts/screenshots/logs. Synthetic fixtures can exercise empty, missing, broken, and successful images.
5. [Current quota guidance](https://developer.spotify.com/documentation/web-api/concepts/quota-modes) retains Premium ownership, five allowlisted users, and developer-account quota buckets. [July changes](https://developer.spotify.com/documentation/web-api/references/changes/july-2026) clarify shared account counting and `QUOTA_EXCEEDED`. Quota buckets are distinct from rolling rate limits; neither their exact capacity nor safe burst size is established here.

**Implementation judgments:** Cache only necessary image metadata, fetch a bounded number of visible uncached artists, deduplicate requests, honor shared cooldowns, and never make artwork a prerequisite for library browsing or playlist creation. A neutral placeholder is truthful when unavailable. Do not issue one fresh Spotify call per card on every render or every list poll. Keep additions within existing Free resources and preserve metadata purge/disconnect lifecycle and the playlist-only saved-library write boundary.

**Not proved by this research:** this app's current token/scopes can successfully fetch either image route; every artist has an image; a new playlist immediately has a cover; image URLs remain valid for a chosen cache interval; endpoint availability implies an affordable quota; any runtime DTO already carries art. These require synthetic boundary tests plus orchestrator-owned, redacted live assertions returning only counts/status/schema booleans. No real metadata, art URLs, or screenshots should enter review context.

## Candidate critique protocol

These are proposed review targets, not published universal thresholds. Independent reviewers should record actual counts and viewport measurements, describe failure impact, and reject improvements that remove MVP capabilities.

- **Hierarchy:** One high-emphasis primary action in the active builder stage and queue task area. Each healthy playlist shows Open plus one secondary Manage entry; no healthy Ready pill. Count visible action groups separately from repeated tag choices, quick slots, and global navigation. Report the baseline and candidate counts instead of declaring “clean”.
- **Queue:** Input and all nine quick-slot positions remain visible on a normal 1440×900 desktop viewport, alongside track identity and Next. Nonessential setup starts collapsed. Keyboard typing, tagging, undo, skip, previous/next, and artist navigation remain usable without opening disclosures. Test long synthetic titles and tags.
- **Builder:** At 390×844 and 360×740 CSS-pixel mobile viewports, an ordinary stage with a few short synthetic tags has its heading/progress, task, and primary action visible without document scrolling. The review list may scroll within a bounded region. Also test 320-pixel width, 200% text, long labels, errors, and open keyboard; vertical scrolling is allowed and preferred to hidden content. No horizontal overflow or obscured focused inputs.
- **Library:** Review a synthetic set with at least 180 groups and a 3,000-track population. The first page must not mount 180 tag editors. Search, group switching, pagination, reset, per-group tagging, range selection, and all-matching selection must still work. Report displayed group count and simultaneous picker count. One contextual bulk picker is the target.
- **Clarity:** A reviewer unfamiliar with implementation must identify what each screen is for and the next useful action from its initial view in five seconds. This is a candidate inspection exercise, not proof of actual user performance. Fail unexplained “ready”, “targeted”, internal cache/proof jargon in the normal happy path, or vague icon-only controls. Do not remove honest failure explanations.
- **Tags:** Inspect ordinary, unused, empty search, rename collision, overlapping merge, delete, and undo states. Default rows show at most one management entry. Confirmation impact counts must reflect distinct songs and remain readable on a phone.
- **Appearance/accessibility:** Test both themes and System; keyboard-focus every disclosure and dialog; check return focus, native semantics, visible selected state, contrast, tap dimensions, and long content. A screenshot alone cannot establish accessibility or mobile keyboard behavior.
- **Art:** Synthetic artist/playlist images, absent images, failures, and refresh states do not shift controls or block interaction. No album image mislabeled as an artist photo; no cropped Spotify visual. Data/API reviewers independently inspect request bounds, cache expiry, purge behavior, and protected writes.

After software checks and synthetic visual proof, the actual user still owns phone-flow acceptance (under one minute) and desk tagging-speed acceptance (roughly 3–5 seconds per familiar song). A reviewer liking the screenshots does not close either criterion.
